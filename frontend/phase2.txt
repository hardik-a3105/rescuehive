# RescueHive — Phase 2: FastAPI Backend and PostgreSQL

Continue development of RescueHive.

Phase 0 created the project foundation.

Phase 1 created the frontend dashboard using mock data.

Now implement the **real backend foundation**.

---

# IMPORTANT PROJECT BOUNDARY

The Webots simulator is NOT part of this phase.

It is maintained separately by another team member.

Do not implement Webots.

Do not create robot controllers.

Do not create simulator-specific assumptions.

The backend should expose clean APIs that can later receive simulator data.

---

# TECHNOLOGY

Backend:

* Python
* FastAPI
* SQLAlchemy
* PostgreSQL
* Pydantic
* JWT
* bcrypt/passlib or an appropriate password hashing library

Use API versioning:

/api/v1/

---

# IMPORTANT IMAGE STORAGE RULE

Do NOT store image/video binary data inside PostgreSQL.

Store files on the filesystem.

Only store:

image_path

inside the database.

This follows the project architecture.

---

# AUTHENTICATION

Implement JWT authentication.

Create:

POST /api/v1/auth/register

POST /api/v1/auth/login

GET /api/v1/auth/me

Passwords must never be stored in plain text.

Use password hashing.

Implement role-based authorization.

---

# MISSION APIs

Create:

GET /api/v1/missions

POST /api/v1/missions

GET /api/v1/missions/{mission_id}

PUT /api/v1/missions/{mission_id}

DELETE /api/v1/missions/{mission_id}

Mission control endpoints:

POST /api/v1/missions/{mission_id}/start

POST /api/v1/missions/{mission_id}/pause

POST /api/v1/missions/{mission_id}/resume

POST /api/v1/missions/{mission_id}/stop

---

# ROBOT APIs

Create:

GET /api/v1/robots

GET /api/v1/robots/{robot_id}

POST /api/v1/robots

PUT /api/v1/robots/{robot_id}

DELETE /api/v1/robots/{robot_id}

Robot commands should be represented as backend services.

Do not connect to Webots yet.

---

# DETECTION APIs

Create:

GET /api/v1/detections

GET /api/v1/detections/{detection_id}

POST /api/v1/detections

PATCH /api/v1/detections/{detection_id}/confirm

PATCH /api/v1/detections/{detection_id}/dismiss

Support filtering by:

* mission
* robot
* type
* status
* confidence

---

# ALERT APIs

Create:

GET /api/v1/alerts

PATCH /api/v1/alerts/{alert_id}/acknowledge

---

# DASHBOARD API

Create an endpoint that returns aggregated mission information.

GET /api/v1/dashboard/summary

Return:

* active mission
* active robots
* explored area
* victim count
* hazard count
* active alerts
* mission duration

---

# HEALTH API

Create:

GET /api/v1/health

Return:

{
"status": "ok",
"service": "rescuehive-backend"
}

# ARCHITECTURE

Keep business logic outside route files.

Use:

routes
schemas
models
services
repositories/database layer

# ERROR HANDLING

Implement clean API errors.

404 — resource not found

400 — invalid request

401 — unauthenticated

403 — insufficient permissions

500 — internal server error

Use consistent response formats.
